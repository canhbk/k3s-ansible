# RabbitMQ Configuration for VN Cluster

## Overview

This directory contains the VN cluster-specific configuration for RabbitMQ deployment.

## Files

- **values.yaml**: Helm values override for the VN cluster

## Key Configuration

- **Storage Class**: `longhorn-vn` (replicated storage)
- **Hostname**: `rabbitmq.ambercare.app`
- **TLS Certificate**: Let's Encrypt Production via `ambercare-app` ClusterIssuer
- **Node Placement**: Storage nodes with `role=storage` label
- **Replica Count**: 1 (single instance)
- **Storage Size**: 2Gi

## Deployment

### Initial Deployment

```bash
helm install rabbitmq oci://registry-1.docker.io/bitnamicharts/rabbitmq \
  --namespace rabbitmq \
  --create-namespace \
  --values values.yaml
```

### Upgrade

```bash
helm upgrade rabbitmq oci://registry-1.docker.io/bitnamicharts/rabbitmq \
  --namespace rabbitmq \
  --values values.yaml
```

## Important Notes

### TLS Certificate Configuration

This configuration uses the **production** Let's Encrypt ClusterIssuer (`ambercare-app`) instead of staging.

**Why Production?**
- Staging certificates (`ambercare-app-staging`) use a fake CA root that's not trusted by browsers or Cloudflare
- Using staging certificates causes Cloudflare Error 526: "Invalid SSL certificate"
- Production certificates are trusted and work properly with Cloudflare and all browsers

**Certificate Details**:
- Issuer: Let's Encrypt R13 (Production)
- Challenge Type: DNS-01 via Cloudflare
- Secret: `rabbitmq.ambercare.app-tls`

### Storage Configuration

The deployment uses Longhorn storage with VN-specific configuration:
- Storage class: `longhorn-vn`
- Replicated storage for data availability
- Scheduled on nodes with `role=storage` label
- Tolerates `dedicated=storage:NoSchedule` taint

## Troubleshooting

### Certificate Issues

If you encounter SSL certificate errors:

1. **Check certificate status**:
   ```bash
   kubectl get certificate -n rabbitmq
   ```

2. **Verify issuer is production (not staging)**:
   ```bash
   kubectl get certificate rabbitmq.ambercare.app-tls -n rabbitmq -o jsonpath='{.spec.issuerRef.name}'
   # Should output: ambercare-app
   ```

3. **Check certificate details**:
   ```bash
   kubectl get secret rabbitmq.ambercare.app-tls -n rabbitmq -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -issuer
   # Should show: Let's Encrypt R13 (not Fake LE)
   ```

### Force Certificate Regeneration

If you need to regenerate the certificate:

```bash
# Delete existing certificate and secret
kubectl delete certificate rabbitmq.ambercare.app-tls -n rabbitmq
kubectl delete secret rabbitmq.ambercare.app-tls -n rabbitmq

# Certificate will be automatically regenerated by cert-manager
# Wait 2-3 minutes for DNS propagation and certificate issuance
kubectl get certificate -n rabbitmq -w
```
